# Sigil

Authorization conformance testing for Soroban.

Soroban contracts decide who may do what through `require_auth`. That surface is
where the expensive bugs live: authorization demanded from the caller instead of
the owning address, a token transfer nobody asserted, an admin gate that any
address satisfies. Contract test suites rarely assert the shape of the
authorization tree at all, and nothing asserts that a client signs entries the
network will actually accept.

Sigil is two halves of one problem:

- **Contract side.** Declare the authorization surface in `sigil.toml`, then
  check the contract against it, first in the `soroban-sdk` test environment and
  then with signed probes on a live network.
- **Client side.** Check that an application's signing path produces auth
  entries the network accepts, using a mock SEP-43 signer.

## Status

Early. This repository is being built in the open and most of it does not exist
yet. What works today:

- `crates/sigil-auth` builds the signing payload for an address-credentials
  authorization entry: `SHA-256(XDR(HashIDPreimage::SorobanAuthorization))`.
  It is pinned byte-for-byte against a fixture generated by the official
  JavaScript SDK, so the two implementations cannot silently drift.
- `crates/sigil-spec` parses `sigil.toml`, the declared authorization surface.
- `crates/sigil-test` compares that declaration against what a contract actually
  demands, and reports the difference.
- Five checks are implemented and proven against deliberately broken contracts:
  **SIG-001** (a state change nobody authorized), **SIG-002** (the wrong address
  authorized), **SIG-003** (a call the spec never declared, authorized anyway),
  **SIG-004** (a declared call that never happened) and **SIG-005** (a declared
  requirement that is not enforced). Each is proven by a `corpus/` pair, and a
  check only counts once it reports the vulnerable half and stays silent on the
  fixed half. Every one of them has been verified by breaking the fixed contract
  and confirming the test fails.
- **SIG-011** emits a finding but has no corpus pair and no test, so it is
  marked `wip` rather than done.

What does not exist yet: the CLI, every live-network probe in
[docs/PROBES.md](docs/PROBES.md), the client-side package, and the remaining
checks in [docs/CHECKS.md](docs/CHECKS.md). The registries are written first on
purpose, so each unit of work has a specification before it has an
implementation. The backlog is in [ISSUES.md](ISSUES.md).

No claim in this README describes code that is not in the repository. If you
find one, it is a bug worth reporting.

## Why the signing payload comes first

Every on-chain probe is downstream of these bytes. A single wrong field or
misordered element produces a tool that confidently reports findings that are
not real, which is worse than having no tool. So the payload is implemented
first and validated against a known-good reference rather than against itself:

    cargo test -p sigil-auth

`fixtures/auth_preimage_v1.json` is generated by `@stellar/stellar-sdk` and is
not hand-written. The test decodes the invocation from that fixture, rebuilds
the preimage in Rust, and asserts both the XDR encoding and the SHA-256 match.

## Layout

    crates/sigil-auth      signing payload construction
    crates/sigil-spec      sigil.toml parser
    crates/sigil-test      assertions against a contract's auth surface
    corpus/                vulnerable/fixed contract pairs behind the checks
    probes/                deployable target + what has actually been run on testnet
    scripts/               fixture generation (JS SDK)
    docs/CHECKS.md         sandbox check registry
    docs/PROBES.md         live-network probe registry
    docs/SPEC.md           sigil.toml directives
    fixtures/              reference vectors from the JS SDK

## What a check looks like

`corpus/caller_not_owner` holds two vaults. Both debit `owner` and credit
`caller`, both call `require_auth`, and neither looks unguarded on a skim. One
asks the caller for permission and then spends someone else's balance:

```rust
pub fn withdraw(env: Env, caller: Address, owner: Address, amount: i128) {
    caller.require_auth();                       // asks the wrong account
    debit_owner_credit_caller(&env, &caller, &owner, amount);
}
```

Against a `sigil.toml` that says `authorizers = ["owner"]`, Sigil reports:

    SIG-002 withdraw: spec requires 'owner' to authorize, but ... did instead

A check that only looked for a missing `require_auth` reports nothing here,
which is why that case has its own test in the pair.
