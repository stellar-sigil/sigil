# Sigil

Authorization conformance testing for Soroban.

Declare what your contract's authorization surface is supposed to be. Sigil
tells you when the contract disagrees.

```toml
# sigil.toml
[[function]]
name = "withdraw"
authorizers = ["owner"]
subinvocations = []
```

```
SIG-002 withdraw: spec requires 'owner' to authorize, but CAAA...FCT4 did instead
```

That finding is a vault which debits `owner` and credits `caller`, and asks the
*caller* for permission. It calls `require_auth`, so it does not look unguarded
in review, and every test passes. Anyone can drain anyone.

## Why this and not a code review

Soroban contracts decide who may do what through `require_auth`. Four things go
wrong there, and none of them look wrong in a diff:

- **Nobody is asked.** A state change with no `require_auth` at all.
- **The wrong party is asked.** The caller consents to their own request, which
  is not permission to spend someone else's balance.
- **More is authorized than intended.** A signature covers the whole invocation
  tree beneath it. A gateway that pays the merchant and then transfers again to
  an address of its choosing used one signature for both.
- **The demand is not enforced.** A function that requires authorization from an
  address the caller supplies is satisfied by the caller naming themselves.

Contract test suites almost never assert the shape of the authorization tree,
so all four survive a green suite.

## Use it

Add the checker to your contract's dev-dependencies, exercise a function, and
assert:

```rust
let env = Env::default();
env.mock_all_auths();
client.withdraw(&caller, &owner, &100);

let bindings = Bindings::new().with("owner", owner.clone());
sigil_test::assert_auth(&env, &spec, "withdraw", &bindings);
```

`mock_all_auths` lets every authorization succeed while recording what was
demanded, so `env.auths()` is the contract's real authorization surface.

Enforcement is a separate question that the recorded surface cannot answer, so
that check takes the outcome of a call made by an identity that should not
qualify. See [docs/CHECKS.md](docs/CHECKS.md).

## What works today

Five checks, each proven against a deliberately broken contract in `corpus/`:

| id | catches |
|----|---------|
| SIG-001 | a state change nobody authorized |
| SIG-002 | the wrong address authorized |
| SIG-003 | a call the spec never declared, authorized anyway |
| SIG-004 | a declared call that never happened |
| SIG-005 | a declared requirement that is not enforced |

A check only counts once it reports the vulnerable half of its corpus pair and
stays silent on the fixed half. Every one has been verified by breaking the
fixed contract and confirming the test fails.

`crates/sigil-auth` builds the signing payload for an authorization entry,
`SHA-256(XDR(HashIDPreimage::SorobanAuthorization))`, pinned byte-for-byte
against a fixture generated by the official JavaScript SDK so the two cannot
drift. The live-network probes are built on it.

## Not done yet

SIG-006 to SIG-012, the live-network probes in [docs/PROBES.md](docs/PROBES.md),
and the client-side signer package. SIG-011 emits a finding but has no corpus
pair, so it is marked `wip` rather than done. The backlog is
[ISSUES.md](ISSUES.md) and the direction is [ROADMAP.md](ROADMAP.md).

No claim here describes code that is not in the repository. CI fails on a
dependency the shipping crate never imports, so the manifest cannot drift from
that either.

## Layout

    crates/sigil-auth      authorization entry signing payloads
    crates/sigil-spec      sigil.toml parser
    crates/sigil-test      the checks
    corpus/                vulnerable/fixed contract pairs behind each check
    probes/                deployable target, and what has run on testnet
    scripts/               fixture generation, dependency guard
    docs/                  check registry, probe registry, spec reference
